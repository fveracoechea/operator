Issue #261. Bun 1.4.3, TypeScript 6.0.3, neverthrow 8.2.0, Effect 4.0.6, unthrown 5.12.1. Checked on Linux.

My recommendation

Favor unthrown's core Result and AsyncResult for these operations.

It passes the same command cases, captures callback defects separately, and supplies tested Oxlint diagnostics without adopting Effect's scheduler. Keep errors, evidence, and retry rules with their owners. This replaces my earlier neverthrow recommendation, not your right to choose.

Ordinary Promise is sufficient for the neverthrow and plain options. Unthrown's eager AsyncResult earns its extra contract by resolving internal failures as Err or Defect, rather than rejecting when a combinator callback throws. The final match still needs an explicit defect policy.

The lint rules help an agent at common mistakes, but do not prove complete handling. Imported producers, dropped chains, and unused bound results still escape the tested must-use check. No library strengthens evidence or retry authority.

Costs to accept. A third Result state, eager async work, an exhaustive matcher vocabulary, and incomplete syntactic lint checks. The core has no runtime dependencies. The Drizzle package does not support SQLite. A Zod async throwing transform leaks an unhandled rejection through Standard Schema, even without the bridge. Neither integration is a reason to adopt it unchanged.

When I would choose differently

Neverthrow with Promise. Choose it for a simpler two-state Result and native async/await. It remains a strong alternative. Callback defects reject to the outer boundary, and the demonstrated Oxlint must-use coverage is weaker.

Plain union. Choose it if avoiding a dependency matters more than standard composition methods. It passed the same behavior tests. It is the closest alternative, not an unsafe fallback.

Effect Result. Choose it if Operator already uses Effect's value tools. A value import does not require running an Effect, but no existing caller needs that ecosystem.

Effect runtime. Reconsider it when real callers need structured concurrency, scoped resources, or typed service requirements across multiple operations. These bounded sequential commands do not establish that need.

Not recommended. Blanket adoption of unthrown's integrations or lint preset, a generic workflow engine, a global error registry, or catch-and-retry around a whole command. Core selection does not select #237's lint policy.

This is a recommendation only. An approved qualifying ADR must precede dependent production adoption. The production CLI still has help and version only.

Compare the working code

The snippets below come from the executable prototype files. Each option calls the same wire decoder, which returns a closed operational error or a verified receipt. The final plain-result projection is only for the shared test and command interface.

All six run the same cases.

Plain TypeScript union

No Result dependency. Native async/await.

Result<T, E> = { ok: true; value: T } | { ok: false; error: E }

Pros

  • Small contract. Standard TypeScript narrowing and early returns.
  • No library runtime, package upgrade, or special async abstraction.
  • The Result wrapper round-trips as JSON without library reconstruction.

Cons

  • Every sequence needs explicit propagation, or a helper that somebody maintains.
  • Mixed error unions can need an explicit return annotation at generic boundaries.
  • No built-in map, combine, or generator composition. A homemade general Result library would erase this option's advantage.

neverthrow with ordinary Promise

Recommended default contract

Result<T, E> is an Ok | Err union. isErr() narrows it. map transforms success, and andThen merges typed error branches.

Pros

  • One standard composition API instead of local Result utilities.
  • Native async/await stays available. No fiber runtime, service container, or scheduling model.
  • Callers can narrow, return an Err, or use match. andThen infers combined errors.

Cons

  • Boundary catches and cancellation still need explicit code.
  • A narrow try { await call() } covers synchronous throws and later rejections. It still must not include our own projection callbacks.
  • Instances have methods. Persist domain payloads, not Ok or Err instances. The name does not guarantee that callbacks cannot throw.

neverthrow ResultAsync

Optional composition tool

ResultAsync<T, E> is a thenable around Promise<Result<T, E>>. It is not a cancellation or resource runtime.

Pros

  • The shortest tested foreign-call, decode, and projection chain.
  • fromThrowable covers synchronous throws and promise rejections from the foreign function.
  • Sync and async steps compose with the same andThen vocabulary. Callers can await the final Result.

Cons

  • One extra async abstraction. It starts work eagerly, unlike a lazy Effect description.
  • fromPromise(call()) cannot catch a throw that occurs while evaluating call().
  • A later map callback can reject the wrapper. No automatic abort propagation, transaction rollback, or safe retry follows from the type.

Effect's lightweight Result value

No Effect execution required

Current Effect 4 uses Result<A, E>. Older Effect 3 examples call its predecessor Either. This option imports only effect/Result and runs ordinary promises.

Pros

  • Functional map, flatMap, match, all, and generator composition.
  • Typed Success and Failure values without adopting Layer, scopes, or fibers.
  • Effect 4.0.6 has no runtime package dependencies.

Cons

  • Imports a much larger package for a small value API, even when the executed module graph is smaller.
  • Plain promises still need narrow exception translation and explicit AbortSignal plumbing.
  • Method-bearing and protocol-bearing values still need plain persistence payloads. Subpath imports need release import-map verification, not only Bun resolution.

Effect runtime, typed failure, and Exit

A broader execution model

Effect<A, E, R> describes an operation lazily. E is its typed failure channel. R is its required services. These examples need no services, so R is never.

Pros

  • Exit and Cause distinguish typed errors, defects, and fiber interruption.
  • Structured concurrency and scoped finalizers are available for callers that need them.
  • A lazy description can compose operations before a single outer execution boundary.

Cons

  • More concepts and runtime code than these sequential operations need.
  • Effect interruption stops local work, not an already-applied GitHub action. It cannot replace durable pending state.
  • The cancellation test found that interruption could mask a synchronous callback defect. A small uninterruptible projection preserves that defect. This is additional runtime-specific policy.
  • Effect result conversion alone does not contain defects. The outer adapter must inspect Exit and Cause.

unthrown Result, AsyncResult, and Defect

Separate defects without a fiber runtime

The promise thunk contains synchronous foreign throws and rejections. Qualification maps those foreign failures into the same conservative operational errors as the other options. A bug in our decoder or projection becomes a Defect instead. The edge names each operational error and sends defects to the existing CLI exception handler.

Pros

  • Callback defects stay separate from modeled operational errors.
  • Exhaustive matching works with the existing plain error union. TaggedError classes are not required.
  • Nine Oxlint rules have executable diagnostics and disabled-rule proof in this experiment.
  • No core runtime dependencies or scheduler. Bun's normal assertions are sufficient.

Cons

  • Not-Ok does not mean Err. A two-state early-return pattern can lose a Defect.
  • AsyncResult is eager. Constructing siblings can start work before an earlier operation succeeds.
  • Must-use lint misses imported producers and dropped chains. Binding a value does not prove handling.
  • The optional no-throw rule would need an exception for this CLI's deliberate defect rethrow.
  • Drizzle is PostgreSQL only. Zod's async throwing transform has a tested rejection leak.

What unthrown's integrations actually cover

Standard Schema and Zod

The tested bridge preserves Zod output inference, transform output, validation issue paths, and sync or async validation. Throwing custom Standard Schema validators become Defect values. Zod's throwing sync transform takes its async fallback, so the sync bridge throws a usage error. The async bridge captures that defect.

A throwing async Zod transform is a separate compatibility limit. The child process prints Defect, then exits 1 on an orphan rejection from Zod's initial sync probe. Calling Zod's Standard Schema validate directly has the same failure. The test keeps this limit visible. Do not claim the bridge contains every validator rejection.

Bun's built-in expect and explicit isOk, isErr, and isDefect guards are enough for these tests. No Vitest package or new assertion framework is needed.

Drizzle is PostgreSQL only

Published @unthrown/drizzle 0.3.0 exports a node-postgres entry, not bun-sqlite. It requires Drizzle ^1.0.0-rc.5-0 and pg ^8.16.0. Source shows a replacement Postgres database and Result-aware transactions, not a generic wrapper for any Drizzle driver.

Operator's SQLite decision stays fixed. A real in-memory Drizzle bun-sqlite test shows that returned unthrown Err and Defect values both commit. An owner-private rollback token can roll back both channels. The PostgreSQL integration does not solve that SQLite boundary for us.

The isolated check pins Drizzle 1.0.0-rc.5-5935859 and pg 8.23.1. It runs the SQLite behavior and loads the Postgres entry, but does not run a Postgres server or claim Drizzle declaration compatibility. These are experiment pins, not production choices.

An Err does not roll back SQLite

The trap is identical in all options

db.transaction(() => {
  writePartialState();
  return err(expectedFailure);
}).immediate();
// A normal return commits, even when it is Err.

The test confirms this for a plain Err, neverthrow Err, and Effect Failure. A runtime can also escape a synchronous transaction if work suspends. Never execute async or external work inside this write transaction.

The state capability must interpret a failed Result before the transaction commits. The scratch adapter throws a private rollback token, lets SQLite roll back, then returns the original typed failure.

Unexpected SQLite failures and programming defects still throw. Only known busy or constraint conditions become typed storage errors. The production Drizzle integration still needs its own verification.

The type cannot force consumption

All options let a caller ignore a successful or failed value. Awaiting a promise is not the same as handling its Result. No option prevents a throwing callback by its name or type alone. 

makeResult();             // Can be ignored.
await makeAsyncResult();  // Awaited, then discarded.
result._unsafeUnwrap();   // Can throw.
result.map(brokenCode);   // Callback defects still exist.

Neverthrow's documented ESLint plugin uses TypeScript parser services. Oxlint's JavaScript plugin API does not currently provide those services. Do not promise that this plugin works in the approved Oxlint toolchain.

What the scratch lint proof establishes

  • Rejected. A floating native promise and a floating ResultAsync, with thenable checking enabled.
  • Rejected. Direct unsafe extraction methods under a scratch property restriction.
  • Still accepted. A discarded synchronous Result and an awaited-but-discarded Result.
  • Not proven. Exhaustive must-use analysis, aliased extraction, or complete control-flow handling.

Assessment used Oxlint 1.87.0 and oxlint-tsgolint 7.0.2003 in scratch only. It adds no production rule, changes no approved #237 policy, and decides no #219 parser exemption.

A library selection does not approve a second linter or a new custom must-use rule. Record that enforcement gap as a cost before adoption.

What would become shared code?

With a plain union, only the small Result type and its constructors have two demonstrated callers and fit a focused lib/result.ts. Do not grow a generic framework around them.

With neverthrow, Effect, or unthrown, import the chosen library directly. Do not add a local forwarding wrapper only to rename its methods.

Workflow errors, refusal reasons, external evidence, effect-result translation, recovery, and output formatting stay with their owners. Transaction interpretation belongs to the state capability, not root lib. The chosen ordered table helper stays separate from error handling.
